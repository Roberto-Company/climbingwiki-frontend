# Decision Log — FrontendApp

Every non-obvious decision made on this project, and why. `HANDOFF.md` says where things stand; `ROADMAP.md` says what's planned; this says **why** things are the way they are, so nobody has to re-derive the reasoning or accidentally undo it. Newest entries at the bottom of each section.

## Project & tooling

### D1. Separate repo/folder from BackendApi
**Decision:** `FrontendApp` is its own folder, not a subfolder of `BackendApi`.
**Why:** Explicit user decision (carried over from the original planning session, predates this log).

### D2. Next.js 16 + TypeScript + App Router + Tailwind v4
**Decision:** Scaffolded with `create-next-app` using TypeScript, App Router, ESLint, Tailwind, `src/` directory, `@/*` import alias, Turbopack.
**Why:** Standard, current, well-supported stack for a server-rendered content site with auth. Tailwind v4 is CSS-first (no `tailwind.config.js`) — confirmed this is the current default, not assumed from older training data.

### D3. Scaffolded into a temp lowercase directory, then moved files in
**Decision:** Ran `create-next-app` against a temporary `climbing-wiki-frontend` folder instead of directly into `FrontendApp/`, then moved the generated files over.
**Why:** `create-next-app` derives the npm package name from the target directory name and rejects capital letters. `FrontendApp` has capitals, so direct scaffolding failed. The package name itself (`climbing-wiki-frontend` in `package.json`) doesn't need to match the folder name, so this was a clean workaround with no lasting effect.

### D4. Next.js 16 renamed `middleware.ts` → `proxy.ts`
**Decision:** Used `src/proxy.ts` (exported function `proxy`), not `middleware.ts`.
**Why:** Verified directly against the Next.js docs bundled in `node_modules/next/dist/docs/` for this exact installed version (16.2.9) rather than relying on memory, since this version postdates this assistant's training data and the package itself ships a warning to that effect (`AGENTS.md` generated by `create-next-app`). `middleware.ts` is deprecated; using it would still work today but is the wrong target for new code.

## Visual direction

### D5. Nature palette, not dark-mode/neon "vibe-coded" look
**Decision:** Light-only theme — warm "chalk" paper background, moss-green primary, sandstone-ochre accent, Fraunces (display serif) + Inter (body sans). No `prefers-color-scheme: dark` block.
**Why:** Explicit user request: a climbing wiki shouldn't default to dark-mode/neon styling that reads as generic AI-generated UI. House design rules also say not to default to dark mode automatically — pick the direction the product actually wants. Verified visually via a Playwright screenshot before proceeding, not just assumed from the CSS.

### D6. Removed default `create-next-app` boilerplate
**Decision:** Deleted the default `public/*.svg` assets and the boilerplate homepage content; replaced with a minimal on-brand placeholder.
**Why:** House anti-template rules ban shipping unmodified library/starter defaults. Kept the replacement minimal (not a full landing page) since full home-page design wasn't in scope for Phase 0 — avoided overbuilding ahead of need.

## Data layer (`lib/api`, `lib/types`)

### D7. Error parsing matches the backend's actual `GlobalExceptionHandler`, not a guess
**Decision:** `ApiError` class with `.status`, `.message`, optional `.validationErrors: Record<string,string>`.
**Why:** Read `BackendApi`'s `GlobalExceptionHandler.java` and `ApiError.java` directly. The backend returns `{message: string}` for most error paths and a raw `Map<field, message>` (no wrapper) for `@Valid` failures — two different shapes on the wire. Modeling this from the real source avoided shipping a client that silently mishandles one of the two shapes.

### D8. `lib/types` mirrors all 40 backend DTOs 1:1, not a hand-picked subset
**Decision:** One TypeScript interface per backend `Request`/`Response` DTO, named identically (`RouteRequest`, `RouteResponse`, etc.), grouped into 19 files + a barrel.
**Why:** Keeps the frontend type contract traceable back to the exact backend record it mirrors — when the backend DTO changes, there's one obvious frontend file to update. Delegated the mechanical mirroring work to a forked subagent (same context, no extra explanation needed) since reading 40 Java files wasn't worth keeping in the main conversation's context.

### D9. `UpsertResult` was not given a TypeScript type
**Decision:** Skipped — it has no frontend equivalent.
**Why:** Traced its actual usage in `FavoriteController`/`FollowController`/`RatingController`/`ListRouteController`: it's consumed entirely on the backend side to pick the HTTP status (`201` vs `200`); only the inner DTO is ever serialized to the client. Modeling it on the frontend would create a type for data that never crosses the wire. Whoever writes `lib/api/favorites.ts` etc. should branch on `response.status === 201`, not look for a `created` flag in the body.

### D10. Nullability on a few fields decided by checking Java validation annotations, not guessed
**Decision:** `UserRequest.role`, `RouteRequest.tagIds`, and several free-text `CragResponse`/`RouteResponse` fields are typed `T | null`.
**Why:** No `@NotNull`/`@NotBlank` on the corresponding Java field means the backend record allows `null` there. Flagged in `HANDOFF.md` as "revisit if real API responses disagree" rather than treated as settled fact, since this was inferred from annotations rather than observed on live data for every field.

### D11. `apiFetch` reads `response.text()` before parsing, not just checking for HTTP 204
**Decision:** Empty-body detection is based on whether the response body is actually empty, not on status code 204 specifically.
**Why:** Found via real end-to-end testing, not reasoning: Spring returns **HTTP 200 with an empty body** (not 204) for controller methods with return type `void` (e.g. `/auth/verify-email`, `/auth/reset-password`). The original code only special-cased 204 and crashed on `response.json()` for these endpoints with `SyntaxError: Unexpected end of JSON input`. This is a general Spring behavior, not specific to these two endpoints — any future `void`-returning endpoint will hit the same path.

## Authentication & session architecture

### D12. httpOnly cookie, never `localStorage`
**Decision:** Session (JWT + display fields) lives in a single httpOnly, `Secure` (in production), `SameSite=Lax` cookie, never exposed to client-side JavaScript.
**Why:** House security rules are explicit: never store sessions in `localStorage` because it's readable by any XSS payload. `ROADMAP.md` from the original planning session already recommended this over `localStorage` for the same reason. This was the one decision explicitly delegated to this assistant's judgment ("I'll let you the decision making") rather than asked as an open question.

### D13. Server Actions for auth, not hand-rolled Route Handlers + client `fetch`
**Decision:** `loginAction`, `registerAction`, `logoutAction`, `verifyEmailAction`, `forgotPasswordAction`, `resetPasswordAction` are all `"use server"` functions in `lib/auth/actions.ts`, wired to forms via React's `useActionState`.
**Why:** Checked the actual Next.js 16 authentication guide (bundled docs, not memory) and confirmed this is the framework's current first-recommended pattern for exactly this shape of problem (form + cookie + redirect). It's also less code than the equivalent Route Handler + client-side `fetch` + manual state management, and Server Actions can set cookies and call `redirect()` directly.

### D14. Session cookie stores the decoded session object, not the raw JWT
**Decision:** Cookie value is `JSON.stringify({token, userId, username, role})`, not just the JWT string.
**Why:** `LoginResponse` from the backend already returns `userId`/`username`/`role` decoded alongside the token — there's no reason to also decode the JWT payload on the frontend to get data we're handed directly. Simpler, and avoids a second code path that has to stay consistent with whatever claims the backend happens to put in the JWT.

### D15. Authoritative session check lives in each protected page, not only in a shared layout
**Decision:** `(account)/profile/page.tsx` calls `verifySession()` itself. There is no `(account)/layout.tsx` doing the gating.
**Why:** The Next.js docs explicitly warn that layouts don't re-run their checks on client-side partial navigation within the same layout subtree — a layout-only guard can be silently bypassed. Checking inside each page (or Server Action / Route Handler) that actually needs the data is the pattern the framework's own docs recommend. `proxy.ts` still does a cheap optimistic redirect on top of this for UX (avoid rendering a protected page just to redirect), but it is not the security boundary.

### D16. `proxy.ts` only checks cookie *presence*, never decodes or calls the backend
**Decision:** The optimistic check in `proxy.ts` is `request.cookies.has(SESSION_COOKIE_NAME)` — no JSON parsing, no JWT decode, no network call.
**Why:** Docs guidance: Proxy/Middleware runs on every matched request, including prefetches, so it should stay cheap and "optimistic" — real authorization happens elsewhere (here, in `verifySession()` and ultimately in the backend's own JWT validation on every API call).

### D17. `proxy.ts` only protects `/profile` so far
**Decision:** `PROTECTED_ROUTES = ["/profile"]`, not the full set of account pages listed in `ROADMAP.md` (`/logbook`, `/favorites`, `/follows`, `/lists`).
**Why:** Those pages don't exist yet — they're Phase 3 ("personal layer") scope. Protecting routes with no content would be speculative. `HANDOFF.md` flags this list as the first thing to extend when Phase 3 adds those pages.

### D18. Skipped Zod for the auth forms despite the house rule to use it for schema validation
**Decision:** Form validation relies on HTML5 input attributes (`required`, `type`, `minLength`) plus the backend's real `@Valid` errors surfaced via `fieldErrors` — no Zod schema layer on the frontend.
**Why:** The backend is already the authoritative validator (`@NotBlank`, `@Email`, `@Size(min=8)` etc. in the Java DTOs) and returns field-level errors in a shape the frontend already parses (`ApiError.validationErrors`). Adding a parallel Zod schema would duplicate those same rules in a second place that can silently drift from the backend's actual constraints — the kind of redundant-source-of-truth problem the codebase's own DRY principle warns against. This is a conscious, called-out deviation from a stated rule, not an oversight.

### D19. `UserNav` is a Server Component, not a Client Component
**Decision:** `src/components/auth/UserNav.tsx` has no `"use client"` directive, despite rendering a logout button.
**Why:** It has no state, effects, refs, or browser APIs — the logout button is a plain `<form action={logoutAction}>` referencing a Server Action, which works from a Server Component. House React rules default new files to Server Components and only add `"use client"` when one of those things is actually needed.

### D20. `forgot-password` shows the reset token on-screen; `verify-email` is a manual token-paste form
**Decision:** Neither flow sends real email. `forgot-password` displays the backend's returned `resetToken` directly in the UI with a visible "Development mode" label and a link straight to `/reset-password?token=...`. `verify-email` is just a bare token input with no way to arrive there from a clicked email link.
**Why:** The backend has no email-sending infrastructure yet (`AuthService` stubs tokens via the response body / logs only — confirmed in `BackendApi`'s own handoff notes). `ROADMAP.md` Phase 1 explicitly scoped this as "wire the three endpoints, no email UI needed yet." This UX is a known, temporary stand-in — replace it once the backend sends real email.

## Operational decisions

### D21. Applied the `alter_auth_tokens.sql` migration to the local dev database
**Decision:** Ran the pending migration (adds `email_verified`, `verification_token`, `verification_token_expires_at`, `reset_token`, `reset_token_expires_at` to `users`) against the local `climbingwiki-db` MySQL container.
**Why:** Without it, the backend's `User` entity fails on *any* query touching `users` (including login), since JPA selects all mapped columns. This blocked all of Phase 1's end-to-end testing. The migration file itself was marked "run this yourself" and a prior session's handoff had already flagged it as pending-with-an-ask-first boundary — asked the user explicitly before running it (`AskUserQuestion`), got approval, then ran it. The other pending migration (`alter_ratings_half_star.sql`) was left untouched — not needed until Phase 3.

### D22. Verified the auth flow against the real backend + database, not just `tsc`/`eslint`/`build`
**Decision:** Started the actual Spring Boot backend and MySQL container, then drove the UI through a real browser (Playwright) for register → login → profile → logout, both `proxy.ts` redirect directions, forgot-password → reset-password (confirming the old password stopped working and the new one worked), and verify-email (confirming the DB flag actually flipped).
**Why:** Type-checking and linting only prove the code is internally consistent, not that it's correct against the real system. This is what caught D11 (the empty-body bug) and D21 (the missing migration) — neither would have surfaced from static checks alone.
